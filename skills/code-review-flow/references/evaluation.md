# 设计范例与验收

范例只演示“同一份材料可以有不同讲法”。全部内容虚构，不携带真实仓库、提交、身份或业务结论；不要把示例的取消模型、结论或章节套进实际报告。默认只读最有关的一份。

## 共用材料 fixture/v1

- E1（虚构需求）：取消确认之后，不得发生新的结果发布；取消前已发布结果是否撤回，需求未定义。
- E2（虚构实现记录）：worker 仅在启动时读取一次任务状态。
- E3（虚构实现记录）：发布步骤不校验取消状态。
- E4（虚构复现记录）：本场景中取消确认后仍发布。示例审查把此缺口列为阻塞项，判断是修复后再合入；这不表示实际执行过测试。
- D1（已有修复建议）：把未取消条件与发布放进同一原子操作，并验证竞争行为。普通的先读再写不提供该保证；建议尚未实现或验证。
- D2（已有后续建议）：通知 worker 停止计算可以另作资源优化，时延与收益未测量，不是此次阻塞；不得据此声称 E4 已解决。

## 四种表达，不是四个必选模式

| 文件（相对于 skill 目录） | 为什么这样表达 | 不应继承什么 |
|---|---|---|
| `examples/mechanism.body.html` | 概念区分 + 双轨时间线，解释取消与发布为什么不是同一事实 | 不强制每篇报告先放概念卡或时间线 |
| `examples/decision.body.html` | 同维度对照先行，揭示两个方案解决的目标不同 | 不把推荐颜色或表格结论当成已验证 |
| `examples/improvement.body.html` | 主修复用定制 SVG 表达约束位置，次要建议减少篇幅 | 不机械要求“一个主建议 + 两张次要卡” |
| `examples/short.body.html` | 一条发现直接说明触发、影响、行动与边界，无图 | 不为显得专业强行扩成图册 |

公共 CSS 和这些文件是可借用的视觉基础。新的问题可以使用新关系、新布局或完全不同的阅读顺序，不需要为它新增 schema 类型。用源码中的注释/标题理解设计取舍，不用逐像素相似度替代解释质量。

## 可复现的机械测试

```bash
node --test "$SKILL_DIR/tests/core.test.mjs"
RUN_BROWSER_TESTS=1 node --test "$SKILL_DIR/tests/browser.test.mjs"
```

第二条需要当前环境的 Playwright/Chromium；可设置 `PLAYWRIGHT_MODULE`、`CHROME_PATH`。未启用浏览器测试时明确 skip，不算通过。命令不安装依赖、不调用模型、不发布内容。浏览器检查也可用现有 harness 执行，但需记录实际覆盖范围。

将示例装配并截图的命令：

```bash
node "$SKILL_DIR/scripts/build-report.mjs" "$SKILL_DIR/examples/mechanism.body.html" "$OUT/mechanism.html" --title '虚构机制讲解'
node "$SKILL_DIR/scripts/capture-report.mjs" "$OUT/mechanism.html" "$OUT/mechanism.png"
```

## 模型与成品评估（不能用单元测试冒充）

用上述 E1–E4/D1–D2 作输入，在不同阅读任务下让模型重新创作，比较其产物而不是复制范例。记录模型、提示、材料版本、输出和实际检查结果。检查：

1. 是否准确保留阻塞程度、原子性条件、未定义问题和“建议未验证”状态？图中的时间/因果有没有被改写？
2. 首屏和主要版面是否服务该读者任务？图是否表达了关系，而不只是段落加框？次要信息能否不妨碍理解主要问题？
3. 长标识符、复杂图、折叠证据和 PNG 下的重要前提是否仍可读？模型是否实际看成品并修正问题？
4. 当任务只需短报告时，是否允许无图、不凑栏目？不同材料能否产生合理不同的结构，而不是只换标题？

额外给一份相互矛盾的审查材料，应明确展示冲突而非悄悄统一结论；给缺少验证记录的材料，应保留未验证而非借范例补事实；给普通“请审查代码”的请求，不应仅交付一张报告替代审查。

严重度被改变、必要前提被省略、待确认被写成已验证，都属于事实保真失败；再漂亮也不通过。版式可以主观比较，事实失真不可由设计分数抵消。一次本地示例渲染只能证明该次生成和检查能工作，不证明所有模型、harness 或任意材料都能稳定达到同样质量。
