# 流程产物：理解包与结论包

理解与结论分开落盘，是因为读者不同：理解包服务"我还有哪里不懂"，结论包服务"我信不信、要不要说"。混成一篇，两边都会读到自己不需要的部分。

**默认载体是 Markdown**；HTML/PNG 只在用户要求时用。Markdown 表达力有限，所以更要靠结构：
- **表**用来并列同维度的东西（需求↔落点、结论↔证据、调用点↔类型），读者可以扫而不是读。
- **图**用 `` ```text `` 围栏画（终端、GitHub、编辑器都能看），只在需要表达**顺序、因果、分支或跨对象关系**时画；一条直线因果链不值得画。需要更漂亮时可用 mermaid，但不作为默认。
- 一条信息只出现一次；不要为了"看起来完整"把同一事实在表和图里各写一遍。

## 01-findings.md（给决定）

目标：每条都能被独立复核。**禁止**解释机制（作者已经知道自己的代码怎么走）。

````markdown
# <repo>#<号> · <PR 标题>（head <短 sha>）

| # | 结论 | 证据 | 置信 | 依据 |
|---|---|---|---|---|
| 1 | <一句话结论> | `[跑过]`/`[读过]`/`[推断]` | 高/中/低 | `文件:行` \| 命令 \| 卡 |

## 需要作者确认
- <置信不足或依赖外部知识的问题>（问句，不是结论）

## 已核对
| 事实 | 方法 |
|---|---|

## 验证边界
- 没跑/没覆盖的东西，以及它对结论的影响
````

排序：先严重度、再置信度降序。低置信不进"结论"表，进"需要作者确认"。置信不足且影响合入时补一句**反证**："如果这条不成立，会以 <具体现象> 暴露"。

## 证据类型

| 标记 | 含义 | 例 |
|---|---|---|
| `[跑过]` | 命令/测试/编译/接口调用的实际输出 | `dotnet test` 全绿；`lsp diagnostics` 报错为空 |
| `[读过]` | 读代码、契约、卡、历史提交得出 | 唯一非测试调用点；生成文件被手改 |
| `[推断]` | 推理未验证 | 后端忽略未知字段，所以现网不炸 |

三条纪律：**跑过 > 读过 > 推断**；能跑的别只读；推断必须说得出验证方法。

## 事实层怎么取

- **符号级事实走 LSP**：`references` 拿调用点、`definitions`/`type_definition` 拿定义与类型、`implementations` 拿接口实现、`diagnostics` 拿编译期问题。它跟随 re-export、遮蔽与跨项目引用，比文本搜索可靠。
- **多仓根下 C# 需要 pin `--solution`**，否则请求不返回（不是报错）：查不到符号时先怀疑语言服务，再怀疑代码。
- **拿不到聚合视图**：当前 harness 若没有代码图能力，影响半径、flow、社区这类查询就没有。用引用 + 调用点采样近似，并写明覆盖范围，例如"仅统计非测试调用点"。
- **契约与生成文件**：先确认改动依赖的契约是否已合并、生成文件是否被手工编辑过（生成文件头会写 "Do not edit manually"）。这决定了"现在的代码是不是下次 codegen 就会消失的状态"。

## 交付闸门

1. 产物落盘到本地评审留档目录（`<pr-id>/`），理解包与结论包分开。
2. 判定载体（PR 评论 / Slack / Markdown / HTML / PNG），**问用户确认**。
3. 只从结论包裁剪生成对外稿；不留机制讲解、过程噪音、本会话才懂的标记。
4. 只有用户要求 HTML/PNG 时才走装配与截图，并完成视觉验收。
