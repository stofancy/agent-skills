# 流程产物：理解包与结论包

理解与结论分开落盘，是因为读者不同：理解包服务"我还有哪里不懂"，结论包服务"我信不信、要不要说"。混成一篇，两边都会读到自己不需要的部分。

**默认载体是 Markdown**；HTML/PNG 只在用户要求时用。Markdown 靠结构补表达力：**表**并列同维度的事实（需求↔落点、结论↔证据、调用点↔类型），**图**用 ` ```text ` 围栏画那条链路（只在顺序/因果/分支/跨对象关系时画，一条直线因果链不值得画），一条信息只出现一次。

## 归属规则（唯一判据）

分界线是「这句话是不是在替读者下判断」：

| 内容 | 归属 | 例 |
|---|---|---|
| 机制、可验证的现象 | 理解包 | 请求体新增了一个字段，取值来自 profile 上的另一个字段；生成文件被手工改过（头部写着 "Do not edit manually"） |
| 判断、动作、严重度、合入意见 | 结论包 | 契约未合并，所以下一次重新生成会抹掉它并让类型检查失败 |

- 理解包**不得出现**：严重度、阻塞/不阻塞、建议、应该、合入判断。
- 结论包**不得出现**：机制讲解、链路图、术语解释（作者已经知道自己的代码怎么走）。
- 同一事实只写一次；结论包引用理解包的节号，不重述。

## 00-understanding.md（给委托方）

目标：读完后**不看 diff 也能讨论这个 PR**。开头先交代"这是什么、要什么"，不允许一上来就做映射。

````markdown
# <repo>#<号> · <PR 标题>（head <短 sha>）

| 项 | 值 |
|---|---|
| 卡 | <TICKET>「<卡 title>」（状态 · Sprint） |
| 依赖 / 契约 | <仓库>#<号>（状态） |
| 快照 | 本产物绑定上面这些 head，不是页面当前状态 |
| 规模 | N 文件 / +a −b（逻辑改动与生成文件、测试分开说） |

## 1. 原始需求（原文，不转述）

> 卡 / PR 描述里与本改动相关的原句，逐条抄下来

一句话概括这个改动要解决什么（我的一句话，可被推翻，不是结论）。

## 2. 需求落点

| 需求（原文） | 落点 | 证据 |
|---|---|---|
| … | `文件:行` | `[读过]` |
| … | **无落点**（可能在别的 PR） | `[读过]` |

## 3. 变更地图

```text
<入口：谁触发> → <中间节点> → <本次改动点> → <下游>
```

| 事实 | 内容 | 来源 |
|---|---|---|
| 入口 | … | `[跑过]` `lsp`/`grep` |
| 本次改动 | … | `[读过]` |
| 调用点 | 非测试 1 处（`文件:行`；原始命中 12 条，含声明与测试） | `[读过]`（数字来自 `[跑过]` `lsp references`） |
| **覆盖范围** | 在 <语言服务> 的 <工程/解决方案> 内、含声明、不含测试 | `[跑过]` `lsp status` |
| **未查方向** | 跨仓库、运行时路径、配置与管道 | — |
| 明确没动 | … | `[读过]` |

**覆盖范围**与**未查方向**是必填两行：它们是读者判断"这份理解能撑到哪"的唯一依据。

## 4. 为什么这么改

- 目的（卡/PR 有记录才写，没有就标 `[推断]`）
- 为什么用这个字段/这条路（替代方案为何没选）

## 5. 边界与后果

只写**可验证的后果**，不给严重度、不给建议：

- 被打破的假设（其它调用方、其它环境、契约版本）
- 没覆盖的场景、没跑的东西

## 6. 从哪读起（可选）

1. `文件:行` —— 看什么

## 7. 开放问题

见结论包的追问台账（同一批问题，不写两处）。
````

**删节判据**：每一节都必须有实质内容，没有就**删掉这一节**。材料不足时用短形态——原始需求原文 + 一行落点 + 边界与后果 + 覆盖范围——不要为凑齐七节而空转。

## 01-findings.md（给决定）

目标：每条都能被独立复核。**禁止**解释机制（作者已经知道自己的代码怎么走）。

````markdown
# <repo>#<号> · <PR 标题>（head <短 sha>）

| # | 结论 | 严重度 | 行动 | 证据 | 覆盖范围 | 证伪条件 | 依据 |
|---|---|---|---|---|---|---|---|
| 1 | <一句话结论> | 阻塞/重要/次要/提示 | <作者要做什么；没有就写"无需动作"> | `[读过]` | <工程内、非测试调用点> | <什么观察会推翻它> | `文件:行` |

**严重度按对本 PR 合入的影响分四档**，与工作量无关（工作量写在"行动"里）：`阻塞`=不该合；`重要`=合前应修；`次要`=可以跟单；`提示`=知道即可。**严重度只在新证据出现时改，并写出依据**。

**把一条从结论表移进追问台账 = "这条还没定"，不是"这条不重要"**——降级不改严重度，所以保真要求（不擅自改严重度）不会被这条规则绕过。

**预测性结论**（"下次重新生成会抹掉它"这类对未发生事件的断言）必须写出证伪条件，或干脆留在台账里等作者确认。

## 机械结果

| 检查 | 结果 | 来源 |
|---|---|---|
| 类型/编译诊断 | … | `[跑过]` LSP `diagnostics`（glob 批次） |
| 平台 CI / 管道 | … | 已有报告链接或"未取到，原因" |

优先取**平台上已经算出来的**结果（CI、管道、测试报告），取不到再本地跑，并写明为什么取不到。

## 需要作者确认（追问台账）

| # | 问句（可判定） | 挂在 | 答 A 改变什么 / 答 B 改变什么 | 阻塞合入 | 状态 |
|---|---|---|---|---|---|
| 1 | … | 结论 2 | 是→升为阻塞；否→降为待验证 | 是 | 已发 / 已答 / 无回应 |

一轮 ≤5 条，按阻塞排序，只问能改变结论或动作的；最多两轮，第二轮注明由第一轮哪条引出。

| # | 上一版 | 这一版 | 依据 |
|---|---|---|---|

## 验证边界

- 没跑/没覆盖的东西，以及它对结论的影响
- 外部状态（卡、契约、门禁、approve）核验时间：<时间>；若状态变化，相关结论需重验
````

排序：先严重度、再证伪条件的强弱。**不写"高/中/低"置信度**——用覆盖范围与证伪条件表达强弱；覆盖不足的条目不做成结论，进追问台账（降级不改严重度）。

## 证据类型（含裁决规则）

| 标记 | 含义 | 例 |
|---|---|---|
| `[跑过]` | 工具/命令/测试**直接给出**的输出 | `lsp diagnostics` 输出；测试全绿；`lsp references` 命中 12 条 |
| `[读过]` | 需要我阅读、分类、取舍才得出 | 生成文件被手工改过；"非测试调用点 1 处"（"非测试"是我判的） |
| `[推断]` | 推理但未验证 | 后端忽略未知字段；必须能说出验证方法 |

- 裁决：**能不能由工具输出直接给出**。是 → `[跑过]`；需要我解释 → `[读过]`。
- 一条事实只允许一种标记；把原始输出数字一并写出，让读者能复核我的分类。
- 否定式结论必须带搜索面：✗"CI 拦不住" → ✓"在 `azure-pipelines-pr.yml` 的 job 列表里未见重新生成并 diff 的步骤"。

## 事实层怎么取

- **符号级事实走 LSP**：`references`（含声明）/ `definition` / `type_definition` / `implementation` / `diagnostics` / `symbols`。
- **先记范围，再下结论**：`status` 记录服务端与工程；声明"没有某能力"前先用 `capabilities` 或 `request` 探测。
- **批量类型检查**：`diagnostics` 传 glob 可一次查一组改动文件（每文件等待约 400ms、一次上限 20 个）；`file:"*"` 的工作区模式按 cwd 判项目类型，多仓根 cwd 下不可用。
- **冷启动窗口的负结果不可靠**：`No references` / 无诊断，在服务未就绪时与真实结果无法区分——先 `status`/`capabilities` 留证，或用文本搜索交叉验证一次，再写进产物。
- **覆盖不了**：影响半径与传递闭包；反射、DI 容器、字符串键、事件总线、序列化边界；跨进程/跨仓（HTTP 边界对面看不见）；运行时路径；架构与社区视图；非代码事实（配置、管道、库表）。
- **禁止句式**："没有影响" → "在 <范围> 内未发现静态引用；跨边界消费点未验证"；"只有 N 处调用"（不附查询点与范围时）；"CI 拦不住" → "在 <搜索面> 内未见 <具体步骤>"。
- **契约与生成文件**：先确认改动依赖的契约是否已合并、生成文件是否被手工编辑过（生成文件头会写 "Do not edit manually"）。这决定了"现在的代码是不是下次 codegen 就会消失的状态"。

## 追问回路

- **链路**：问题清单只经委托方转给作者，产物不直接外发。
- **四要素**：可判定的问句 / 挂在哪条结论 / 两个答案各自改变什么 / 是否阻塞合入。
- **答案回来改哪**：(a) 补事实 → 更新理解包对应节 + 结论包"已核对"；(b) 确认或否定 → 改结论的覆盖范围与证伪条件，从台账移走；(c) 作者说法与代码不符 → **现象描述不改**，结论包新增"作者意图 vs 代码行为不一致"。
- **作者的回答是"作者陈述"，不是 `[跑过]`**。
- **不追溯改判**：追问中学到的团队偏好**只对下次生效**，写进惯例库（与留档放一起），下次遇到同类改动先读它——它改变的是下一次的判据，不是这一次的结论。
- **无回应的判据是事件不是时钟**：作者 push 新 head 未答 → 先做增量复审并标"head A→B 未答"；作者 approve/合入 → 窗口关闭，未答项写进验证边界；委托方宣告结束 → 同上。

## 增量复审

同一 PR 第二次看时：

1. 先重验外部状态（卡、契约、门禁、approve 数）并记时间——上一版的快照不是现在。
2. 只对照上一版快照，逐条给 `remain / addressed / skipped`；`skipped` 要显式写出来，避免被当成"修好了"。
3. 结论表里被推翻的条目删掉或降级，并保留被推翻的理由。

## 交付闸门

1. 产物落盘到本地评审留档根下的 `<pr-id>/`，理解包与结论包分开。留档根由使用者约定一次（本机固定一个）并复用；**不得落在被评审仓库的工作树里**——那会污染它自己的 diff。
2. 判定载体（PR 评论 / Slack / Markdown / HTML / PNG），**问用户确认**。
3. 只从结论包裁剪生成对外稿；不留机制讲解、过程噪音、本会话才懂的标记。
4. 目标载体不支持表格/折叠/颜色时，**允许重排成短句列表**（判断内容不许改）；不得为了塞进表格把多子句结论压成管道符文本。
5. 只有用户要求 HTML/PNG 时才走装配与截图，并完成视觉验收。
