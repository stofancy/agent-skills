# 飞书消息形态：按消息类型的短模板与反例

本文件用于"先确定这条消息要完成什么"之后判断正文形态。按消息类型给出**短模板 + 反例**。核心原则：**群消息给结论和动作，复杂证据下沉到 PR 评论/文档并给链接。**

## 反 AI 味一页纸（从 tech-doc-writing 抽取，只保留即时消息相关）

- **结论优先**：第一行就是结论，不是"我审查了/验证了/我们做了"。
- **去流水账**：每句都为读者的行动服务；可调换顺序读感不变的段落删掉。
- **去表演**：不自我表扬、不"没有人问的问题"辩护、不强行总结升华。
- **过程信息预算**：默认 0 段过程。仅当某句过程直接影响读者信任或行动时才留一句。
- **术语按读者展开**：内部代号、A/B、P0/P1 只有接收者共享上下文时才保留，否则展开成直接动作。
- **格式克制**：emoji、连续粗体小标题、水平分隔线、加粗专段默认不用。

## 结果通知（默认类型）

用途：把结论发群。读者看完要能说"合/不合/改哪/等谁"。

模板：
```
<结论一句话：能不能合 / 是什么状态>
<影响对象 / 需谁处理>
<必要的动作或链接>
```

反例：
```
## XX 评审结论
审查了三个 PR（用了模型 X + 逐条核实源码 + 跑测试）。
**结论：** 核心实现质量高，仅一个 P1 需修后合并。
**已核实为误报的点：** ...
**验证：** build ✓ 测试 ✗ ...
**总评：** 整体经得起推敲...
```
（第一行是过程；误报/验证/总评都属过程信息。）

正例：
```
模型升级这三个 PR 里，service #65 先别合：启动迁移错误调用了只应在切换时执行的升级脚本，会引起 CI 失败。web-admin #34 和 web-portal #39 无阻断，可合。证据见各 PR 评论。
```

## 状态同步

用途：告诉群里当前到哪一步，不需要谁决策。

模板：
```
<事情> 现在 <状态>。接下来 <下一步>。
```

反例：把背景、为什么、过程全塞进去。正例只给状态+下一步。

## 决策请求

用途：请群里对选项拍板。给少量互斥选项 + 明确推荐。

模板：
```
问题：<一句话>
- A：<代价>
- B：<代价>
推荐 A。理由是 <一句>。
```

若接收者不共享 A/B 含义，把选项展开成具体动作，不用代号。

## 行动指派

用途：明确谁做什么。

模板：
```
<谁>，请 <具体动作>。<完成的判断标准/期限，若有>
```

## 纠错消息

用途：推翻/更正之前发的一条。

模板：
```
抱歉，上一条关于 <事项> 的结论有误。正确结论是 <结论>。请 <动作>。
```

反例：先解释"我之前是怎么得出结论的"，或长篇复盘。不发过程。

## review 邀请 vs review 结果（区分）

- **邀请别人 review**：用 [gitea-pr-review.md](gitea-pr-review.md) 的模板（PR 元数据 + review 重点）。
- **发已完成的 review 结论**：用上面的"结果通知"模板，**不要复用邀请模板**。

## 复杂信息下沉

群消息里出现以下内容时，移出正文、放 PR 评论或文档，正文只留一句结论 + 链接：
- 完整审查过程、验证清单、测试明细
- 逐条 P0/P1/P2 长清单（除非接收者必须逐条决策）
- 架构设计论证、备选方案对比
- 上下文窗口、行号、代码片段等实现细节
