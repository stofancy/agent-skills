# 深入检查

仅在对应问题存在时读取本节；基础必要性、载体、触发和权限判断见技能入口，不重复执行完整审核。

## 职责重组与退役

当两个 Skill 长期针对同一输入、修改同一产物并重复同一判断时，比较合并与收窄；不同事实所有者的协作不是重复。拆分应对应可独立触发和验收的工作，而非统一行数阈值。

删除、移动或重命名前查调用方、用户入口、adapter、自动 hook 和引用。生成物必须回到源或生成器修改，不直接修镜像。保留原始历史证据；失效的操作指令应退出当前路由，不能只改根文件而让下层继续指挥任务。

## 引用与执行资产

- 抽查从入口到实际操作的引用链，查找下层文件中与当前边界冲突的强制步骤、弱化断言或过期宿主假设。短入口不证明整个包精简或可靠。
- 路由写清读取条件，避免要求每次加载所有 reference。深层链接只有在实际任务需要时跟进，不为目录形式新增文件。
- 确定性命令需说明工作目录、必要输入、环境和失败语义。大段参数/模式放按需资料；短且稳定的调用可留根入口。
- 核对脚本是否能解析、依赖是否存在、失败是否可识别、数据写入/清理是否限定本次对象；已有脚本不等于已验证工作流。复制配方或输出字符串不能替代可观测结果。
- 路径、模型、价格、版本、资源和授权等易变事实应查询对应所有者；历史记录需要注明适用范围，不能形成长期权限。

## 触发与行为验证

针对本次改动选择代表请求：直接命名、未命名但意图相同、共享关键词的相邻任务、普通执行而非治理，以及多步任务中的局部触发。不用毫不相关的请求证明路由精确。

发生复杂职责或边界变化时，若实际评测有必要，使用相同模型/工具/基线和原始材料，隔离运行，避免把预期答案喂给评测者。先核对正确性、完整性与权限，再看调用、耗时和返工。构造场景或一次运行不能证明稳定性能收益。

区分结构有效、语义一致、触发合理、行为通过和宿主真实加载；缺少哪种证据就限制哪种声明。测试应验证可观察行为，不为固定标题、措辞或“另一个测试存在”新增测试。
